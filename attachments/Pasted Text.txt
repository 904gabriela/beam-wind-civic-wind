NEXUS — MASTER DEVELOPMENT SPECIFICATION

ROLE

You are the primary software architect and developer for Nexus, my personal, private AI roleplay and storytelling application.

Your job is not simply to make a UI that resembles an AI chat application.

You are building a complete story-management and context-management engine whose purpose is to make long-form AI roleplay feel coherent, persistent, intelligent, and easy to use.

The central philosophy of Nexus is:

The user should not have to manually manage the AI’s context. Nexus should manage it for them.

The LLM should be the renderer of the story.

Nexus itself should be responsible for:

* characters
* personas
* worlds
* lore
* relationships
* memories
* story state
* context retrieval
* prompt construction
* branching
* continuity
* generation styles
* automatic discovery of characters
* automatic memory creation
* long-term story persistence

The application is for one user and private/local use.

Do NOT build Nexus as a social platform.

2. WHAT NEXUS IS

Nexus is a personal AI storytelling environment.

It should combine ideas from applications such as:

* Tipsy-style AI roleplay
* SillyTavern-style character/world importing
* branching chat systems
* persistent story memory
* FictionLab’s Memory Matrix concept
* local LLM applications

However:

Nexus is NOT a copy of any of them.

Take the useful concepts and build an integrated system around them.

The most important difference is that Nexus should not feel like a collection of disconnected modules.

For example, I do NOT want:

Character → completely separate object

Lorebook → completely separate object

Persona → completely separate object

Memory → completely separate object

Chat → completely separate object

Instead, everything should belong to the same Story/Scenario ecosystem.

Bakugo

2. associate it with the current Story

10. LORE VS MEMORY

These are fundamentally different.

Lore

Static information.

Examples:

U.A. High School is located in Japan.
Bakugo's Quirk is Explosion.
The world contains professional heroes.

Memory

Things that happened during the current story.

Examples:

Reiko kissed Bakugo.
Reiko told Bakugo a secret.
Bakugo promised not to tell anyone.
Reiko and Bakugo had an argument.
Bakugo later apologized.

Lore describes the world.

Memory describes what happened.

Do not merge them into one undifferentiated database.

However, both should feed the same Context Engine.

13. WHAT SHOULD BECOME A MEMORY?

The system should detect meaningful changes.

For example:

User:

Reiko leaned forward and kissed Bakugo before whispering, “I never told anyone this, but…”

AI:

Bakugo froze…

The system should recognize that something important happened.

Potential memory:

Event:
Reiko kissed Bakugo.
Event:
Reiko revealed a personal secret to Bakugo.
Relationship impact:
High.
Emotional significance:
High.

Another example:

Reiko dropped her phone.

This should probably NOT become a permanent memory.

Another:

Reiko moved to Japan permanently.

This should probably become a memory/fact.

Another:

Bakugo promised Reiko he would protect her.

This should become a promise/relationship memory.

⸻

14. MEMORY CONFIDENCE

Do NOT blindly commit everything the AI sees.

This is extremely important.

Use confidence levels.

High confidence

Clearly stated or directly observed.

Automatically save.

Medium confidence

Reasonably supported but potentially ambiguous.

Save as editable/soft memory.

Low confidence

Inference, speculation, joke, metaphor, uncertain interpretation.

Do not permanently commit automatically.

Example:

Observed:
Bakugo looked away.
Inference:
Bakugo was embarrassed.

The first is an observation.

The second is an interpretation.

Do not treat them equally.

16. MEMORY DEDUPLICATION

The system must avoid producing:

Bakugo made a promise to protect Reiko.
Bakugo vowed to protect Reiko.
Bakugo told Reiko he would keep her safe.

as four separate memories.

These should potentially consolidate into one:

Bakugo promised Reiko he would protect her.

Implement semantic deduplication/consolidation.

32. STREAMING

Responses should stream token-by-token.

The user should see the response being generated naturally.

The architecture should also allow generation state to survive temporary client disconnects if practical.

For example:

Generation starts
       ↓
Server owns generation
       ↓
WebSocket streams tokens
       ↓
Client disconnects
       ↓
Generation continues
       ↓
Client reconnects
       ↓
Completed generation becomes available

This is especially useful when accessing Nexus from another device on the local network.

33. CHAT BRANCHING

Chats should be trees, not simple linear logs.

Each message should have a parent.

Conceptually:

A
│
B
├── C
│   └── D
│
└── C2
    └── D2

If the user:

* edits a message
* regenerates a response
* chooses another response
* forks a conversation

the original branch should remain.

Do not overwrite history.

A useful model:

Message
- id
- chatId
- parentId
- role
- content
- createdAt

And:

Chat
- rootMessageId
- activeLeafId
- canonLeafId

The visible conversation is reconstructed by walking from the active leaf to the root.

⸻

34. REGENERATION

If the user regenerates an AI response:

Original response
       ↓
New response

create a sibling branch.

Do not delete the old response.

The user should be able to switch between them.

⸻

35. EDITING

If the user edits an earlier message:

Do not mutate the entire conversation destructively.

Create a new branch from that point.

This preserves the original timeline.

44. OBSERVATION VS INFERENCE

This distinction should exist in the data model.

Example:

Observation:
Bakugo looked away.
Inference:
Bakugo was embarrassed.

The first can be stored confidently.

The second should have lower confidence unless explicitly confirmed.

This is critical for preventing memory corruption.

Manual user edits should have higher authority than automatic extraction.

68. IMPORTANT MEMORY RULE

Never allow the Memory Engine to become the source of truth for the actual conversation.

The hierarchy is:

CHAT = primary source
MEMORY = structured derived knowledge
LORE = static world knowledge
CHARACTER = structured character knowledge
STORY STATE = current derived situation

Memories can be regenerated from source information when necessary.

70. IMPORTANT ROLEPLAY RULE

Nexus should not force story outcomes.

It should preserve character behavior.

For example:

If a character is canonically aggressive, Nexus should not make them suddenly romantic merely because a preset says “Romantic.”

Generation presets control writing style, not fundamental character identity.

Character definitions and story continuity have higher authority.
